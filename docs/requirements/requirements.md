# Loop Engineering Agent — 需求文档

## 1. 概述
- **项目**：Loop Engineering Agent（LEA）
- **版本**：1.0
- **日期**：2026-06-12
- **作者**：需求分析（AI 辅助）

### 1.1 项目愿景

构建一个基于 Loop Engineering 原则的自主编程智能体 CLI 工具，通过收敛反馈闭环驱动软件从需求到交付的完整流程。该智能体可接入主流大模型厂商（智谱、DeepSeek、OpenAI、Anthropic 等），内置 dev-workflow-skills 技能体系，并系统性解决三个核心工程挑战：

1. **上下文溢出**：长时间执行超出窗口限制导致中断
2. **进度丢失**：上下文清除后无法恢复任务进度
3. **自主执行**：任务未完成时无需人工介入，AI 自主推进至交付

### 1.2 核心设计决策

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 运行形态 | CLI 工具 | 开发者友好，可脚本化，与 CI/CD 集成 |
| 技术栈 | TypeScript/Node.js | 前后端统一，npm 生态丰富，异步 I/O 天然适合 AI 调用 |
| 编排机制 | 状态机 + 持久化 | 阶段流转清晰，状态可恢复，适合收敛闭环 |
| 技能整合 | 内置解释执行 | 直接读取 SKILL.md 运行时解释，保持技能的声明式本质 |
| 模型集成 | LiteLLM Proxy | 统一 100+ 模型 API，内置路由/回退/计费，减少自建适配成本 |
| 安全边界 | 分级权限 | 类似 Claude Code 的权限模式，安全与灵活兼顾 |
| 上下文策略 | 混合（边界压缩 + 子代理隔离） | 阶段边界自动压缩，任务内子代理隔离上下文 |

## 2. 干系人与用户角色

| 角色 | 描述 | 核心关注点 |
|------|------|-----------|
| 开发者 | 使用 LEA 执行编程任务的软件工程师 | 效率、可控性、代码质量 |
| 项目管理者 | 监控项目进度的技术负责人 | 进度可视、风险预警、交付可控 |
| AI 系统运维 | 部署和维护 LEA 实例的运维人员 | 稳定性、资源消耗、模型成本 |
| 技能开发者 | 编写和维护 SKILL.md 的知识工程师 | 技能可插拔、格式兼容、调试便利 |

## 3. 功能需求

### FR-001：多模型厂商统一接入
- **描述**：系统应当通过 LiteLLM Proxy 统一接入智谱、DeepSeek、OpenAI、Anthropic 等主流模型厂商，对上层提供一致的 API 接口
- **优先级**：Must
- **来源**：用户输入
- **验收标准**：
  - Given 已配置 LiteLLM Proxy 和至少一个厂商 API Key，When 发起模型调用，Then 系统成功返回响应
  - Given 智谱 GLM-4 模型已配置，When 调用 chat completion，Then 返回格式与 OpenAI 格式兼容
  - Given DeepSeek-R1 模型已配置，When 调用推理任务，Then 正确处理 reasoning_content 字段
- **依赖**：无

### FR-002：模型路由与回退
- **描述**：系统应当支持基于任务类型、成本、延迟的模型路由策略，并在主模型失败时自动回退到备选模型
- **优先级**：Must
- **来源**：用户输入 + 隐含需求
- **验收标准**：
  - Given 配置了主模型和回退模型，When 主模型调用超时或返回错误，Then 自动切换到回退模型重试
  - Given 配置了路由规则（简单任务→低成本模型，复杂任务→高能力模型），When 收到任务，Then 按规则选择模型
  - Given 模型调用失败，When 连续失败超过 3 次，Then 标记该模型为不可用并通知用户
- **依赖**：FR-001

### FR-003：工作流状态机引擎
- **描述**：系统应当实现基于有限状态机的工作流引擎，管理从需求分析到测试交付的阶段流转，支持门控检查和阶段回退
- **优先级**：Must
- **来源**：用户输入（Loop Engineering 原则）
- **验收标准**：
  - Given 工作流已初始化，When 按顺序推进阶段，Then 状态按 需求→设计→评估→任务→开发→测试 流转
  - Given 当前阶段制品不满足门控条件，When 尝试推进，Then 拒绝推进并提示缺失条件
  - Given 测试发现 Bug，When 反馈给开发，Then 状态回退到开发阶段
  - Given 评估发现致命问题，When 需要返回需求或设计，Then 状态回退到对应阶段
- **依赖**：无

### FR-004：工作流状态持久化
- **描述**：系统应当将工作流状态持久化到本地存储，支持进程中断后从断点恢复执行
- **优先级**：Must
- **来源**：用户输入（问题2：清除上下文丢失进度）
- **验收标准**：
  - Given 工作流正在执行，When 每个阶段完成时，Then 状态自动持久化到磁盘
  - Given 工作流因中断（手动停止/崩溃/上下文溢出）停止，When 重新启动，Then 自动识别未完成的工作流并提示恢复
  - Given 恢复了中断的工作流，When 继续执行，Then 从上次持久化的阶段和状态继续，不重复已完成的工作
  - Given 持久化文件损坏，When 尝试恢复，Then 报告损坏并提示从最近的完整检查点恢复
- **依赖**：FR-003

### FR-005：技能解释执行引擎
- **描述**：系统应当内置 SKILL.md 解释器，直接读取和执行技能定义文件，无需预编译
- **优先级**：Must
- **来源**：用户输入（整合 skills 体系）
- **验收标准**：
  - Given skills 目录包含有效的 SKILL.md 文件，When 启动工作流，Then 自动发现并加载所有技能
  - Given 工作流进入某个阶段，When 需要执行对应技能，Then 读取 SKILL.md 内容作为 LLM 的指令 prompt
  - Given 技能引用了其他技能（如 workflow-skill 引用 req-analysis-skill），When 执行到引用点，Then 正确调度被引用的技能
  - Given SKILL.md 包含 references/ 目录下的参考文件，When 执行技能时，Then 将参考文件内容一并注入上下文
- **依赖**：FR-001

### FR-006：上下文边界压缩
- **描述**：系统应当在工作流阶段边界自动压缩上下文，将已完成阶段的详细交互压缩为结构化摘要，释放上下文窗口
- **优先级**：Must
- **来源**：用户输入（问题1：上下文溢出）
- **验收标准**：
  - Given 阶段一（需求分析）已完成，When 进入阶段二（设计），Then 阶段一的详细交互被压缩为需求文档摘要
  - Given 压缩后的摘要，When 后续阶段需要回溯需求细节，Then 能从摘要中获取关键信息
  - Given 当前上下文接近窗口限制（>80%），When 任意时刻，Then 触发紧急压缩
  - Given 压缩发生，When 用户查询已压缩内容，Then 能从持久化存储中恢复完整历史
- **依赖**：FR-003, FR-004

### FR-007：子代理上下文隔离
- **描述**：系统应当为每个任务/技能执行创建独立的子代理上下文，子代理完成后仅将结果摘要返回主控，防止上下文污染
- **优先级**：Must
- **来源**：用户输入（混合上下文策略）
- **验收标准**：
  - Given 开发阶段有多个任务，When 执行每个任务时，Then 在独立子代理上下文中运行
  - Given 子代理完成任务，When 返回结果，Then 仅传递任务完成报告和关键产物，不传递完整交互历史
  - Given 子代理执行失败，When 超过重试限制，Then 将失败信息摘要返回主控
  - Given 子代理需要访问项目文件，When 读取文件，Then 通过共享文件系统访问，不通过上下文传递
- **依赖**：FR-003, FR-005

### FR-008：自主执行循环
- **描述**：系统应当支持自主执行模式，在工作流启动后无需人工介入，自主推进阶段直至交付，仅在配置的检查点暂停
- **优先级**：Must
- **来源**：用户输入（问题3：无需人工介入自主执行）
- **验收标准**：
  - Given 工作流以自主模式启动，When 进入每个阶段，Then 自动执行直至阶段完成
  - Given 配置了检查点（如每阶段完成后），When 到达检查点，Then 暂停并通知用户审批
  - Given 用户批准检查点，When 继续执行，Then 推进到下一阶段
  - Given 未配置检查点（完全自主），When 执行工作流，Then 从需求到交付全程无人工介入
  - Given 自主执行中遇到无法解决的错误，When 重试 3 次后仍失败，Then 暂停并请求人工介入
- **依赖**：FR-003, FR-006, FR-007

### FR-009：收敛反馈闭环
- **描述**：系统应当实现开发-测试收敛闭环，测试发现的 Bug 自动反馈给开发修复，直至 Bug 数量收敛为零
- **优先级**：Must
- **来源**：用户输入（Loop Engineering 原则）
- **验收标准**：
  - Given 测试阶段发现 Bug，When 反馈给开发，Then 自动创建修复任务并进入开发阶段
  - Given 修复完成，When 重新测试，Then Bug 数量应递减
  - Given 同一区域连续 3 轮未收敛，When Bug 数量不减反增，Then 暂停并升级给用户
  - Given 连续 3 轮无新 Bug，When 声明迭代稳定，Then 推进到下一迭代或完成
- **依赖**：FR-003, FR-008

### FR-010：分级权限控制
- **描述**：系统应当实现分级权限模型，对文件写入、命令执行等敏感操作进行权限控制
- **优先级**：Must
- **来源**：用户输入 + 安全需求
- **验收标准**：
  - Given 文件读取操作，When 在任何模式下，Then 自动允许
  - Given 文件写入操作，When 在自动模式下，Then 根据权限配置决定是否需要确认
  - Given 危险命令（如 rm -rf、git push --force），When 尝试执行，Then 必须用户明确确认
  - Given 用户配置了权限白名单，When 执行白名单内的操作，Then 自动允许
- **依赖**：无

### FR-011：进度可视化与报告
- **描述**：系统应当实时显示工作流进度，包括当前阶段、已完成任务、待处理任务、Bug 统计等
- **优先级**：Should
- **来源**：隐含需求
- **验收标准**：
  - Given 工作流正在执行，When 用户查看进度，Then 显示当前阶段、迭代、任务状态
  - Given 测试发现 Bug，When Bug 被记录，Then 显示 Bug 趋势（递减/递增）
  - Given 工作流完成，When 生成总结报告，Then 包含所有阶段制品的索引和完成状态
- **依赖**：FR-003

### FR-012：技能热插拔
- **描述**：系统应当支持在不重启的情况下动态加载、更新和卸载技能
- **优先级**：Should
- **来源**：隐含需求（技能迭代）
- **验收标准**：
  - Given 新技能文件放入 skills 目录，When 工作流未执行时，Then 自动发现并注册新技能
  - Given 技能文件被修改，When 下次执行该技能时，Then 使用最新版本
  - Given 技能被标记为禁用，When 工作流执行时，Then 跳过该技能
- **依赖**：FR-005

### FR-013：断点续跑与崩溃恢复
- **描述**：系统应当在进程崩溃或手动中断后，能从最近的成功检查点恢复执行，不丢失已完成的工作
- **优先级**：Must
- **来源**：用户输入（问题2：上下文清除丢失进度）
- **验收标准**：
  - Given 进程在开发阶段崩溃，When 重新启动，Then 识别到未完成的工作流并提示恢复
  - Given 用户选择恢复，When 从检查点继续，Then 跳过已完成的阶段，从崩溃点继续
  - Given 崩溃发生在子代理内部，When 恢复时，Then 重新执行该子代理任务
  - Given 持久化存储包含完整的阶段制品，When 恢复时，Then 所有已交付的文档和代码均保留
- **依赖**：FR-004

### FR-014：制品版本管理
- **描述**：系统应当对每个阶段产出的制品进行版本管理，支持查看历史版本和差异对比
- **优先级**：Should
- **来源**：隐含需求（Loop Engineering 原则：状态持久化）
- **验收标准**：
  - Given 阶段产出制品，When 制品被更新，Then 保留历史版本
  - Given 闭环回退修改了需求文档，When 查看文档，Then 能看到修改前后的差异
  - Given 多次迭代的制品，When 查看历史，Then 能追溯每次变更的时间和原因
- **依赖**：FR-004

### FR-015：LiteLLM Proxy 配置管理
- **描述**：系统应当提供 LiteLLM Proxy 的配置管理，包括模型列表、API Key、路由规则和成本预算
- **优先级**：Must
- **来源**：用户输入
- **验收标准**：
  - Given 配置文件包含模型和 API Key，When 启动系统，Then 自动连接 LiteLLM Proxy
  - Given 配置了成本预算，When 累计调用成本超预算，Then 暂停执行并通知用户
  - Given 配置了路由规则，When 发起调用，Then 按规则选择模型
  - Given API Key 无效，When 尝试调用，Then 报告错误并尝试回退模型
- **依赖**：FR-001

## 4. 非功能需求

### NFR-001：上下文窗口利用率
- **描述**：系统应当将有效上下文利用率维持在 80% 以下，超过时自动触发压缩
- **优先级**：Must
- **来源**：用户输入（问题1）
- **验收标准**：
  - Given 长时间执行场景，When 上下文使用超过 80%，Then 自动压缩或启动子代理
  - Given 压缩后，When 上下文使用降至 50% 以下，Then 继续正常执行
- **依赖**：FR-006, FR-007

### NFR-002：状态恢复可靠性
- **描述**：进程中断后状态恢复的成功率应达到 99%
- **优先级**：Must
- **来源**：用户输入（问题2）
- **验收标准**：
  - Given 正常的持久化文件，When 恢复工作流，Then 100% 成功恢复到断点状态
  - Given 持久化文件部分损坏，When 恢复，Then 回退到最近的完整检查点
- **依赖**：FR-004, FR-013

### NFR-003：自主执行时长
- **描述**：系统应当支持至少 8 小时的连续自主执行，不因上下文溢出或状态丢失而中断
- **优先级**：Must
- **来源**：用户输入（问题3）
- **验收标准**：
  - Given 配置了合适的模型和上下文策略，When 执行大型项目工作流，Then 持续运行 8 小时以上不中断
  - Given 8 小时执行期间，When 发生上下文溢出或模型调用失败，Then 自动恢复并继续
- **依赖**：FR-006, FR-007, FR-013

### NFR-004：启动性能
- **描述**：CLI 工具从启动到可交互的时间应低于 3 秒
- **优先级**：Should
- **来源**：行业标准
- **验收标准**：
  - Given 系统已安装，When 执行 lea 命令，Then 3 秒内显示交互界面
- **依赖**：无

### NFR-005：安全审计
- **描述**：所有敏感操作（文件写入、命令执行）应当被记录到审计日志
- **优先级**：Should
- **来源**：安全最佳实践
- **验收标准**：
  - Given 任何文件写入或命令执行，When 操作发生，Then 记录到审计日志
  - Given 审计日志，When 查看日志，Then 包含时间戳、操作类型、目标路径、授权结果
- **依赖**：FR-010

### NFR-006：跨平台兼容
- **描述**：系统应当在 Windows、macOS、Linux 上运行
- **优先级**：Must
- **来源**：用户环境（Windows 开发环境）
- **验收标准**：
  - Given Windows 10/11 环境，When 运行 LEA，Then 所有功能正常
  - Given macOS 环境，When 运行 LEA，Then 所有功能正常
  - Given Linux 环境，When 运行 LEA，Then 所有功能正常
- **依赖**：无

### NFR-007：模型调用延迟
- **描述**：单次模型调用（不含生成时间）的框架开销应低于 500ms
- **优先级**：Should
- **来源**：用户体验
- **验收标准**：
  - Given 模型调用请求，When 从请求发出到收到首个 token，Then 框架开销（不含网络和模型推理时间）低于 500ms
- **依赖**：FR-001

## 5. 约束

| ID | 约束 | 理由 |
|----|------|------|
| C-001 | 使用 TypeScript/Node.js 技术栈 | 用户选择；前后端统一，npm 生态丰富 |
| C-002 | 通过 LiteLLM Proxy 接入模型 | 用户选择；统一 API，减少自建适配成本 |
| C-003 | 技能以 SKILL.md 格式定义，运行时解释执行 | 用户选择；保持技能的声明式本质 |
| C-004 | 必须在本地运行（非云服务） | CLI 工具定位；数据隐私和离线能力 |
| C-005 | 状态持久化使用本地文件系统 | 零外部依赖；轻量部署 |
| C-006 | 兼容现有 dev-workflow-skills 技能体系 | 用户输入；整合现有资产 |

## 6. 假设

| ID | 假设 | 若假设错误的后果 |
|----|------|-----------------|
| A-001 | LiteLLM Proxy 可本地部署或远程访问 | 需要自建模型适配层，增加开发工作量 |
| A-002 | 主流模型厂商 API 保持 OpenAI 兼容格式 | 需要为每个厂商编写独立适配器 |
| A-003 | SKILL.md 格式稳定不变 | 需要增加格式版本检测和兼容处理 |
| A-004 | Node.js 运行时足够支撑长时间自主执行 | 可能需要考虑进程管理和守护进程 |
| A-005 | 用户已安装 Node.js 18+ 和 LiteLLM | 需要增加安装引导和依赖检查 |
| A-006 | 子代理模式可通过 LLM API 的多轮会话实现 | 需要额外的进程隔离机制 |

## 7. 术语表

| 术语 | 定义 |
|------|------|
| LEA | Loop Engineering Agent，本项目名称 |
| Loop Engineering | 收敛反馈闭环工程，以闭环迭代替代线性流程的软件交付方法 |
| Skill | 技能，以 SKILL.md 定义的声明式任务执行规范 |
| 阶段 | 工作流中的一个逻辑步骤，如需求分析、设计、开发等 |
| 门控条件 | 阶段推进前必须满足的退出条件 |
